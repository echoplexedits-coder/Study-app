Admin access and role troubleshooting

Roles live in the D1 `roles` table, keyed by lowercased email. The row is only
applied when the signed-in identity is provider-verified (`roleFor` in
`src/worker/db.ts`):

- `local:*` (username/password) accounts never receive an email-based role.
- `google:*` requires `email_verified === true`.
- Freebuff and other provider identities are trusted.

Consequences:

1. A password account with the admin's email stays a student. It cannot claim
   the role or merge into the provider account.
2. Password sign-up is refused for an email that already belongs to a provider
   account or to a role row (`emailConflict`).
3. A role row by itself does not make a password account an admin. The account
   must sign in through Google or Freebuff.

If an expected admin sees the student badge:

1. Check the sign-in method first. Password sign-in can never be admin.
2. Check that the `roles` row uses the exact lowercased Google or Freebuff
   account email.
3. Check that the account is not suspended; suspension blocks every API call.
4. Check the Google account reports a verified email. An unverified Google
   address is deliberately treated as a student.

Do not add or delete role rows blindly. In particular, the old advice in this
file about a missing production role and an `alex@example.com` row described a
local-test artifact and must not be applied to the live database.

The last admin cannot be demoted, suspended or deleted. The shared check is
`isLastAdminChange` in `src/worker/db.ts`, used by role changes, account
suspension and self-deletion; `tests/admin-guard.test.ts` covers it.

Verification without a database console:

1. Sign out and back in with the intended provider account.
2. Settings should show "Admin — can edit the library".
3. The library should offer New deck and admin uploads.
4. A different account must still show "Student — read-only library" and receive
   403 from admin endpoints.

For Google admin access, enable 2-Step Verification on that Google account. The
app does not perform that check; it is an account-security step.
